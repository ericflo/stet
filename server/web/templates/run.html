Run entries

An entry in the competition is a data editor: a program that edits the round's raw pages into training data. Somebody has to run each one on the round's fresh pages, and it must not be the organisers alone. A runner does that, in a sandbox with no network, and uploads the script the editor writes. This is the work the competition is shortest of: every runner means more entries in each round and a sooner score for everyone.

CompeteVerify scoresRun entries

This runs strangers' programs on your machine. They run in a sandbox, described below, and every one is public code from an account tied to a GitHub identity. That is a deterrent, not a guarantee. Use a machine you could reinstall without loss.

Do this

  1. Install, on Linux

    The installer brings Python {{.Season.Environment.Python}}, PyTorch for your GPU and the {{len .Season.Environment.Packages}} libraries editors are promised. You also need bubblewrap from your distribution's packages.

    $ curl -fsSL {{.BaseURL}}/install.sh | sh

  2. See whether the machine is fast enough

    Every editor is promised a machine at least as fast as a floor. This measures yours against it, in under a minute, and says what falls short if anything does. Run it with the GPU doing nothing else.

    $ stet doctor
$ stet bench

  3. Make an account and link GitHub

    Running editors is for accounts with a name behind them.

    $ stet login --handle yourname
$ stet login --github

  4. Start

    It tests its own sandbox, then takes work. Until you are established it is given scripts to grade; after {{$d.Establish}} {{plural $d.Establish "grade that agrees" "grades that agree"}} with other people's, editors start arriving by themselves.

    $ stet verify --edits

  5. Leave it running

    As a service it starts with the machine, comes back if it stops, and upgrades itself between jobs.

    $ stet service install --edits

What the sandbox does

stet verify --edits tests it before taking any work, and will not start without it.

An editor gets

Its own files, and a fixed machine

Its bundle, the round's pages and the model files it named, all read-only. {{.Season.Machine.Cores}} cores, {{.Season.Machine.MemoryGB}} GB of memory, one GPU with {{.Season.Machine.GPUMemoryGB}} GB of its memory, {{.Season.Machine.ScratchGB}} GB of scratch space held in that memory, and {{howlong .Scale.EditSeconds}}, after which everything it started is killed.

An editor does not get

Your network or your files

No network at all. None of your files, your other processes, or your machine's name. It can see the paths of the directories it was given, and so the name of the account stet runs as.

What it cannot contain

The GPU driver and the kernel

Using a GPU means talking to its driver. The sandbox is namespaces and resource limits, not a virtual machine, and a flaw in the driver or the kernel is outside it.

What comes out

One file of plain data

The edit script: document numbers and byte ranges. The harness checks it before anything else reads it, and nothing in it is ever executed.

What happens next

  1. first round or two

    You grade, and become established

    Your grades are compared with other verifiers'. After {{$d.Establish}} that {{plural $d.Establish "agrees" "agree"}} the account is established: from then on its work makes scores, and it is handed editors.

  2. each round

    You are handed editors to run

    One at a time, never your own, never the same entry twice. The machine fetches any model files the entry names (up to {{bytes .Season.Assets.MaxBytes}}, cached), runs the editor for at most {{howlong .Scale.EditSeconds}}, and uploads the script.

  3. between editors

    You grade other runners' scripts

    Never one you wrote yourself. A second person runs each editor too, and when two runs disagree a third is asked.

  4. when the round settles

    Every run is published

    Who ran what, on which GPU, how long it took and what it scored. Your GPU time and the editors you ran are on the verifiers board.

Questions runners ask

the details →
Does it keep itself up to date?

Yes. A new release can change the libraries editors are promised, so a runner that holds no job installs it and starts again, using the installer from this site. Turn that off with --no-upgrade or STET_AUTO_UPGRADE=0; then it stops taking work when it falls behind, and stet upgrade brings it back.

How much disk and network will it use?

About 1 GB a round for the pages, and the model files entries name: up to {{bytes .Season.Assets.MaxBytes}} an entry, kept in a cache trimmed at 40 GB (STET_ASSET_CACHE_GB changes that).

What if an editor fails on my machine?

If the editor is at fault, that run scores 0 for the entry, and another person's run shows whether it was the editor. If the machine is at fault (a full disk, a GPU something else is using) the job is handed back and nothing is held against the entry.

My machine is under the floor.

Then it can still verify scores, which needs only the GPU. The floor exists so that an editor that finishes in time on one runner finishes in time on all of them.

Can I run it in a virtual machine or a container?

If the GPU is passed through and stet doctor is happy, yes, and a virtual machine is the stronger wall. The sandbox itself needs unprivileged user namespaces and a systemd user session.

Why must I be established first?

A runner's script decides somebody's score. An account earns that by showing, on work that can be checked, that its machine computes what everyone else's does.
